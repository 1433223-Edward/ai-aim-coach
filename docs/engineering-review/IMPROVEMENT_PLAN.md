## P0 必修：先建立可信、可重现的 Demo

### P0-1 上传契约与分析入口防线（建议第一个任务）

**业务价值**：避免错误数据产生看似精确的建议，保障原始证据可信；也是最容易用可复现失败证明改进效果的一项。

**范围**：SessionUpload、session_validator、analysis dataset validation、API 错误映射；保留现有合法 schema 的兼容策略，不覆写历史数据。

**执行**：嵌套 schema 或等效严格验证；有限数值、正 sensitivity/radius、时间类型与单位、事件容器和字段类型；显式检查 Session/Attempt/事件时间边界、第一次 HIT 结束、HIT 几何一致、计数和尺寸。区分零移动合法样例与缺失轨迹；原始输入不能因“纠错”被静默修改。分析入口针对导入/已有 DB 的数据也需校验或明确隔离，不只保护 HTTP 上传。

**验证/完成标准**：本轮四个内存负例都得到受控错误；HTTP 非法 payload 返回可定位的 422，不产生 500、不落库；合法采集、零移动、首击命中、多次 MISS、时间边界通过；有效 fixture 指标保持一致；使用临时 DB 验证异常前后行数不变。

**主要风险**：严格契约可能拒绝旧数据；应将 legacy schema 通过只读适配器转换为派生副本，并保留来源/缺失字段，而非放宽新写入规则。工量：约 1–2 工程日，含边界回归，非承诺。

### P0-2 固定实验身份、协议和请求级证据快照（建议第二个任务）

**业务价值**：回答“建议到底基于哪次实验”，防止刷新和并发上传导致混合证据。

**范围**：前端 experiment controller、Storage、Analysis Runtime、Tools、PlanRequest/Response；新增协议/实验状态模型可能涉及迁移。

**执行**：后端生成不可碰撞 experiment ID；协议记录 targetCount、sensitivity/repeat、训练区/输入模式策略和版本；schedule 一次生成并持久化，恢复按已确认 Session 推进。plan 请求显式传 experiment_id；开始时载入确定的 session ID 集合，计算一次不可变 analysis snapshot，全部工具查询同一 snapshot；返回 snapshot ID、样本量和不完整标识。快照是请求隔离，不是跨请求全局可变缓存。

**验证/完成标准**：刷新/双标签页不增加重复条件或混合协议；缺失/不完整实验有明确状态；同次规划期间插入新 Session，所有工具的 snapshot ID 和样本数保持不变；后续请求可看到新快照。历史 exp_001 不自动重分组，先报告不一致并用新协议新 ID 开始。

**主要风险**：迁移和恢复策略不当会破坏旧证据；必须先做只读备份校验，新增记录保留原 ID 和来源，不推测未知历史顺序。工量约 2–3 日。

### P0-3 离线可复现回归与 Demo fixture（建议第三个任务）

**业务价值**：让没有 Key、没有本地 DB 的评审者也能验证采集到证据的核心价值；消除依赖作者电脑状态的测试。

**范围**：analysis/test、后端测试、Agent mock、新 fixture/导入说明、依赖与 CI 配置；所有写入指向临时 DB。

**执行**：把 main/verify 脚本转为真正可收集的 test_*；固定最小手算样例验证四指标、样本标准差和 finding 边界；为旧 9/180 数据保留来源 hash 和独立 adapter，黄金结果与旧输出比较。DB/API 测试覆盖保存/读取/404/409/422，禁止使用作者原库。Fake client 覆盖多工具消息顺序、未知工具、缺参、坏 JSON、超轮、空答、无证据答与供应商超时。真实 Qwen smoke 单独显式 opt-in，不能混进离线默认测试。

**验证/完成标准**：干净环境一条测试命令能实际收集并执行测试，返回非零测试数量；全程不联网、不要求 Key、不改原库；CI 执行同一命令。Demo seed 在明确的独立 DB 中可重复导入，冲突可诊断、不会覆盖。历史 schema 0.1 的黄金输出保持原样。

**主要风险**：把现有输出当全部真值会掩盖算法问题，因此同时需要可手算样例和不变量；不要为了让旧断言通过去修改真实数据。工量约 1–2 日，P0-1/2 各自附带自身测试，不能等此任务才补。

### P0-4 Agent runtime 失败隔离与证据门槛

**业务价值**：Demo 中工具失败可解释、可恢复，建议可追溯；体现 Agent 应用工程而非 prompt 拼接。

**范围**：experiment_planner.py、tools.py、PlanResponse 与错误响应。

**执行**：dispatcher 严格验证参数对象、字段、有限数值、比较数量与唯一性；未知 sensitivity 返回结构化工具错误，让模型有一次受限纠正机会。区别“失败工具尝试”和“成功取证”。建议前强制获得同一快照的必要证据；空数据或无证据降级为信息不足，不能返回无依据的成功建议。校验空答、截断/拒答、工具调用消息结构；明确最后一轮的收尾策略。设置应用级总时限、单调用超时/重试、总 tool 数和 token 预算；保留 SDK 默认行为的显式配置。修正返回类型注解。

**验证/完成标准**：mock 测试覆盖全部错误路径及六轮边界；无法用零工具输出普通实验建议；失败分类和 request ID 对前端可见；工具 trace 包含参数、成功状态、耗时和 snapshot ID。真实供应商验证作为单独 smoke，记录模型和日期，不把 mock 结果称为真实模型通过。

**主要风险**：自动重试增加成本/延迟；强制证据门槛不能误拒绝无需证据的说明性回答，需先限定 plan endpoint 的职责。工量约 1–2 日，依赖 P0-2 快照接口。

### P0-5 启动解耦与可靠保存反馈

**业务价值**：缺 Key 时仍能采集和离线分析；网络失败时用户知道数据在哪里，避免展示过程无故卡死。

**范围**：planner 客户端初始化、main.py 生命周期、run.ps1、frontend 保存与 planner UI。

**执行**：启动不因可选 Agent Key 缺失而失败，延迟创建客户端；Agent 不可用返回清晰服务状态；用 lifespan 初始化 DB。上传增加超时、可见 pending/saved/failed 状态和持久 pending queue，重复上传同 ID/同内容可恢复，冲突内容仍拒绝；保留下载 fallback。规划不得读入尚未确认的数据，pending 状态明确提示；处理请求取消、重试、训练与规划互斥策略、pointerlockerror 和 fallback 失败。将 3 次 Demo 协议与 20 次历史协议显式区分。

**验证/完成标准**：无 Key 启动能访问训练页和 Session API；Agent 明确不可用；断网、慢请求、服务端已写但客户端丢响应、刷新恢复、Esc、完成九轮后再开新实验都有可理解行为；浏览器实际演练确认自动下载/手动导出可用；不覆盖任何旧 Session。

**主要风险**：客户端队列容量与隐私、本地状态升级和幂等语义；进度保存需区分“采集完成”和“服务端确认”。工量约 1–2 日，依赖 P0-2 状态契约。

**价值**：仅在确有远程演示/多人需求时扩大访问；**范围**：鉴权、授权隔离、请求体/速率/成本限制、TLS、持久卷、备份恢复与部署配置；**验证**：跨用户拒绝访问、重启数据仍在、负载/成本边界和恢复演练；**风险**：当前无用户隔离的 API 会暴露 Session，并允许消耗模型费用。完成这些条件前保持本地演示，不将“可以绑定公网地址”当成部署完成。是否需要 PostgreSQL/任务队列依据负载证据决定。

## 推荐交付顺序与验收门

先做 P0-1，并同时建立最小独立 fixture；随后 P0-2 固定证据与实验状态；第三项 P0-3 完成离线回归和 Demo 数据。再依次落地 P0-4/5，完成可信可演示基线。按个人开发估计，P0 共约 7–11 工程日，包含任务重叠后的粗略估计，实际取决于兼容策略和环境验证。

每项改造独立可审查变更，附触发案例、前后行为、验证命令和结果；不通过清空数据、改写旧输出或重命名原始文件解决问题。跨 schema 的派生物写新位置并附来源清单，真实数据迁移前先备份验证。

P0 完成后 Demo 应能演示：无 Key 训练和离线分析 → 有效数据保存与异常拒绝 → 指定实验快照 → 工具调用轨迹 → 带证据和限制的建议 → 网络/模型失败的明确反馈。真实 Qwen 录制另行运行，标注日期、模型和快照；离线录制标明 mock，不混淆两者。

P1 优先 trace/评估与结构化计划，其次根据测量优化性能与打包；P2 按真实需求选择。无需先换框架、上微服务、引入向量库或做预测模型。
